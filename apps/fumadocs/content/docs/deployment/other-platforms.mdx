Short, honest notes for platforms we didn't write a full guide for. All of them can run StryveForms using the same two Dockerfiles as the Coolify and Railway guides — none of this requires Railpack.

## Dokploy

[Dokploy](https://dokploy.com) is Docker Compose–native, similar in shape to Coolify.

1. **Create → Compose**, paste or point at `docker-compose.yml` (the plain one, not `docker-compose.coolify.yaml` — Dokploy doesn't understand Coolify's `SERVICE_*` magic variables).
2. Dokploy generates a `.env` file next to the compose file from its built-in variable editor — set `BETTER_AUTH_SECRET` (`openssl rand -base64 48`), `DATABASE_URL`, `APP_URL`/`BETTER_AUTH_URL`/`CORS_ORIGIN`, and the optional variables from [Overview](/docs/deployment/overview#environment-variables) there.
3. Dokploy proxies through Traefik under the hood — add the domain for the **web** service (port `3002`) from its **Domains** tab; it issues the TLS certificate for you.
4. Deploy. Each service's logs are visible separately in the Dokploy UI.

Source: [Dokploy Docker Compose docs](https://docs.dokploy.com/docs/core/docker-compose).

## CapRover

[CapRover](https://caprover.com) deploys from a `captain-definition` file (JSON, `schemaVersion: 2`) rather than reading `docker-compose.yml` directly — you create one app per container.

For each of `web` and `server`, create a CapRover app and a definition file pointing at the matching Dockerfile:

```json
{
  "schemaVersion": 2,
  "dockerfilePath": "./apps/server/Dockerfile"
}
```

(swap in `./apps/web/Dockerfile` for the web app). Set the **Captain Definition Path** in each app's **Deployment** tab if you keep both files in the repo (e.g. `./captain-definition-server`, `./captain-definition-web`) rather than the default `./captain-definition`. CapRover's build context is always the repo root even when the Dockerfile lives in a subdirectory, which matches how both Dockerfiles here already expect to be built (`context: .`).

You'll need a separate Postgres app (CapRover's one-click apps include Postgres) or an external managed database, a persistent volume on the server app for `/data/storage`, and CapRover's own HTTPS/domain settings for the web app only.

Source: [CapRover captain-definition docs](https://caprover.com/docs/captain-definition-file.html).

## Render

Render reads a `render.yaml` **Blueprint** from the repo. A minimal one for StryveForms:

```yaml
databases:
  - name: stryveforms-db
    plan: starter

services:
  - type: web
    name: stryveforms-server
    runtime: docker
    dockerfilePath: ./apps/server/Dockerfile
    dockerContext: .
    healthCheckPath: /
    envVars:
      - key: DATABASE_URL
        fromDatabase:
          name: stryveforms-db
          property: connectionString
      - key: BETTER_AUTH_SECRET
        generateValue: true
      - key: APP_URL
        fromService:
          name: stryveforms-web
          type: web
          property: host
      - key: TRUST_PROXY
        value: "true"
    disk:
      name: stryveforms-storage
      mountPath: /data/storage
      sizeGB: 10

  - type: web
    name: stryveforms-web
    runtime: docker
    dockerfilePath: ./apps/web/Dockerfile
    dockerContext: .
    healthCheckPath: /
    envVars:
      - key: SERVER_URL
        fromService:
          name: stryveforms-server
          type: web
          property: host
```

`generateValue: true` is Render's own equivalent of Coolify's `SERVICE_BASE64_64_*` — it creates a random secret for you. A service with a persistent `disk` can't be horizontally scaled on Render (same constraint noted in [Overview → Scaling notes](/docs/deployment/overview#scaling-notes)); switch `STORAGE_DRIVER` to `s3` first if you need multiple server instances. Set `BETTER_AUTH_URL`/`CORS_ORIGIN` the same way as `APP_URL` above.

Source: [Render Blueprint YAML reference](https://render.com/docs/blueprint-spec). We didn't deploy this blueprint for real — check the `fromService`/`fromDatabase` property names against the current reference before trusting it as-is.

## Fly.io

Fly is the odd one out here: a Fly **app** maps one-to-one with one Dockerfile/image, and `fly.toml` doesn't support "one config, several Dockerfiles" the way a Compose file does. You need **two separate Fly apps**, each with its own `fly.toml` at the repo root pointing at a different Dockerfile:

```toml
# fly.server.toml
app = "stryveforms-server"
[build]
  dockerfile = "apps/server/Dockerfile"
[http_service]
  internal_port = 3000
  force_https = true
[[mounts]]
  source = "stryveforms_storage"
  destination = "/data/storage"
```

```toml
# fly.web.toml
app = "stryveforms-web"
[build]
  dockerfile = "apps/web/Dockerfile"
[http_service]
  internal_port = 3002
  force_https = true
```

Deploy each with `fly deploy --config fly.server.toml` / `fly deploy --config fly.web.toml` — paths in each are relative to the repo root (the build context), not your current directory. Add Postgres with `fly postgres create` then `fly postgres attach --app stryveforms-server`, which sets `DATABASE_URL` on the server app for you. Fly volumes are single-region and not automatically redundant — the docs recommend at least two volumes per mount if the data matters, so either accept that risk for `/data/storage` or use S3-compatible storage (Fly also sells Tigris object storage) instead.

Source: [Fly.io monorepo guide](https://fly.io/docs/launch/monorepo/), [Fly.io Postgres](https://fly.io/docs/postgres/).

## Plain Docker Compose on a VPS

The repository's `docker-compose.yml` is already written for this: `bun run docker:up` builds and starts `web`, `server` and `postgres` with a local volume. The only thing it doesn't do is terminate HTTPS — put one of these in front of it.

### Caddy

Caddy gets you automatic HTTPS from one block — add this `Caddyfile` next to the compose file and run Caddy as a fourth service (or on the host):

```
forms.example.com {
  reverse_proxy web:3002
}
```

Caddy requests and renews the certificate itself the first time it starts, as long as port 80/443 on your VPS reach it and DNS already points at the server.

### Traefik

If you're already running Traefik, add labels to the `web` service in `docker-compose.yml`:

```yaml
  web:
    # ...existing config...
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.stryveforms.rule=Host(`forms.example.com`)"
      - "traefik.http.routers.stryveforms.tls.certresolver=letsencrypt"
      - "traefik.http.services.stryveforms.loadbalancer.server.port=3002"
```

Either way, set `TRUST_PROXY=true` on the **server** (already the default in `docker-compose.yml`) and point `APP_URL`/`BETTER_AUTH_URL`/`CORS_ORIGIN` at the final `https://` domain.
