This is the recommended way to run StryveForms on [Coolify](https://coolify.io): one Compose resource with three services (`web`, `server`, `postgres`), using the `docker-compose.coolify.yaml` file already in the repository. Read [Overview](/docs/deployment/overview) first if you haven't.

## 1. Create the resource

1. In your Coolify project, **New Resource → Public/Private Repository**.
2. Point it at your StryveForms repository and branch.
3. Build Pack: **Docker Compose**.
4. **Docker Compose Location**: `/docker-compose.coolify.yaml` (not the plain `docker-compose.yml` — that one is for local/VPS use and doesn't know about Coolify's magic variables).

## 2. Set the domain

Open the **web** service's settings and set its domain, including the container port suffix:

```
https://forms.example.com:3002
```

Coolify reads the port suffix and fills in `SERVICE_URL_WEB_3002` with the resulting URL — that's what the compose file uses for `APP_URL`, `BETTER_AUTH_URL` and `CORS_ORIGIN` on the **server** service. Leave the **server** and **postgres** services without a domain; they stay on the private network and are only reachable from `web`.

<Callout type="warn">
  Every place that needs this URL must reference the exact same variable name, `SERVICE_URL_WEB_3002` (including the `_3002` suffix). Coolify stores a generated value under its full name — a bare `${SERVICE_URL_WEB}` elsewhere in the compose file resolves to an empty string instead of your domain. This is already handled correctly in the committed file; if you copy pieces of it elsewhere, keep the full name everywhere.
</Callout>

## 3. Fill in the optional variables

Coolify generates and manages for you automatically, with no action needed:

- `SERVICE_USER_POSTGRES` / `SERVICE_PASSWORD_POSTGRES` — the database credentials
- `SERVICE_BASE64_64_AUTH` — a random 64-character string used as `BETTER_AUTH_SECRET`

These persist across redeploys (Coolify doesn't regenerate them on every deploy) and are visible under the resource's **Environment Variables** tab if you need to read them for a manual `pg_dump` or similar.

Everything else is optional and defaults to "off" — fill in only what you need, under the resource's environment variables:

| Group | Variables |
| --- | --- |
| File storage (S3) | `STORAGE_DRIVER=s3`, `S3_BUCKET`, `S3_REGION`, `S3_ENDPOINT`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` |
| Outgoing email | `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_SECURE`, `MAIL_FROM` |
| Captcha | `HCAPTCHA_SITE_KEY` / `HCAPTCHA_SECRET_KEY`, `RECAPTCHA_SITE_KEY` / `RECAPTCHA_SECRET_KEY`, `TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY` |
| Telegram integration | `TELEGRAM_BOT_TOKEN` |

See [Overview → Environment variables](/docs/deployment/overview#environment-variables) for what each one does.

## 4. Deploy

Click **Deploy**. Coolify builds both images from their Dockerfiles, starts `postgres`, waits for its healthcheck, starts `server` (which runs database migrations automatically, then waits for its healthcheck), then starts `web`. Open your domain — the first visit runs onboarding.

## Persistent storage

Two named volumes are already declared in the compose file:

- `stryveforms-postgres` — the database
- `stryveforms-storage` — uploaded files, signatures, generated PDFs (only used when `STORAGE_DRIVER=local`, the default)

Coolify prefixes these with the resource name internally; you'll see them under **Storages** on the resource. Back them up the same way described in [Overview → Backups](/docs/deployment/overview#backups) — Coolify doesn't currently script this for you.

## Verifying the compose file yourself

Before deploying, you can check the file is syntactically valid and see exactly what Coolify will build:

```bash
docker compose -f docker-compose.coolify.yaml config
```

The Coolify-only magic variables (`SERVICE_URL_WEB_3002`, `SERVICE_BASE64_64_AUTH`, `SERVICE_USER_POSTGRES`, `SERVICE_PASSWORD_POSTGRES`) show up as empty strings when you run this locally — that's expected; only Coolify's own deploy step fills them in.

## Upgrading

Push to the branch Coolify watches (or click **Redeploy**). Coolify rebuilds both images and does a rolling restart; the server's migration step runs again automatically and is a no-op if there's nothing new to apply.
