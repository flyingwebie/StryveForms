[Railpack](https://railpack.com) is Coolify's buildpack-style builder (no Dockerfile needed). It works for StryveForms, but **only with a specific setup** — plain autodetection gets it wrong for this repo. This page explains exactly what to set, and what we verified by actually running Railpack against this codebase.

<Callout type="warn">
  Use this page if you want Railpack specifically (e.g. faster builds, no Dockerfile maintenance). If you just want something that works with the least fuss, use [Coolify — Docker Compose](/docs/deployment/coolify-docker-compose) instead — it uses the Dockerfiles that already ship in this repo and needs no extra configuration.
</Callout>

## Why not just point Railpack at `apps/web` or `apps/server`?

StryveForms is a Bun workspace monorepo: the root `package.json` declares the workspaces and a `catalog` of shared dependency versions, and only `bun.lock` at the repo root knows how to resolve them. We tested Railpack's own autodetection (`railpack info <dir>`) against this repo to confirm what actually happens:

**Base directory = `apps/server` or `apps/web`:**

```
⚠ No node package manager detected, using npm
↳ Using npm package manager
```

Railpack can't see `bun.lock` or the root `package.json` from inside a sub-folder, so it falls back to plain `npm install`. That fails here: the app's `package.json` depends on internal packages via `workspace:*` (e.g. `"@StryveForms/api": "workspace:*"`) and catalog versions (e.g. `"zod": "catalog:"`), which only resolve inside the Bun workspace at the repo root. **Don't set Base Directory to a sub-app** on this repo.

**Base directory = repo root, no other configuration:**

```
↳ Using bun package manager
↳ Found workspace with 13 packages
↳ Deploying as vite static site
↳ Output directory: dist
```

From the root, Railpack correctly detects Bun and the workspace — but then it has to guess *which* of the 13 packages is "the app", and guesses wrong: it picks a generic Vite static-site shape (serving a `dist` folder with Caddy), which matches none of our actual deploy targets (the server is a long-running Bun process; the web app is a TanStack Start SSR server, not a static site).

## The setup that works

Set **Base Directory to the repo root** for both services, and explicitly override the build and start commands — either as literal fields in Coolify's Railpack build settings, or as `RAILPACK_BUILD_CMD` / `RAILPACK_START_CMD` service environment variables (both are read by Railpack; we verified both paths with `railpack info`). With an explicit start command, Railpack stops guessing a deploy shape entirely and uses yours.

### Server

| Setting | Value |
| --- | --- |
| Base Directory | `/` (repo root) |
| Build Command | `cd apps/server && bun run build` |
| Start Command | `bun packages/db/src/migrate.ts && bun apps/server/dist/index.mjs` |
| Port | `3000` |

### Web

| Setting | Value |
| --- | --- |
| Base Directory | `/` (repo root) |
| Build Command | `cd apps/web && bun run build` |
| Start Command | `bun apps/web/.output/server/index.mjs` |
| Port | `3002` |

With these set, `railpack info .` reports exactly the plan we want:

```
↳ Using bun package manager
↳ Found workspace with 13 packages
↳ Custom start command detected, skipping Caddy start
↳ Bun runtime detected

Steps
──────────
▸ install
  $ bun install --frozen-lockfile
▸ build
  $ cd apps/server && bun run build     (or cd apps/web && bun run build)

Deploy
──────────
  $ bun packages/db/src/migrate.ts && bun apps/server/dist/index.mjs
```

That's the correct install (whole workspace, frozen lockfile), build (the one app), and start command — no guessing left.

Then set the same environment variables as [Overview → Environment variables](/docs/deployment/overview#environment-variables) lists, pointing `SERVER_URL` on the web service at the server's private Railpack-assigned address, and give **web** (only) a public domain.

## Why no `railpack.json` in this repo

Railpack config files (`railpack.json`) live at the project's base directory, and we just established that both services need Base Directory set to the **same** repo root. A single `railpack.json` there can't hold two different build/start commands for two different services — whichever app wrote it last would silently break the other. The explicit Build/Start Command fields above apply per-service without this collision, so that's what we recommend instead of a committed config file.

If your platform lets you point a service at a specific config file path (Railway's legacy Config as Code did; check whether Coolify's Railpack builder offers the same), you could create `apps/server/railpack.json` / `apps/web/railpack.json` with a `deploy.startCommand` and reference each explicitly — but the Build/Start Command fields achieve the same thing with one less moving part, so we didn't add these files.

## Known limitation: native/wasm assets

The server depends on `@resvg/resvg-wasm` (PDF rendering) and ships two `.ttf` font files under `packages/api/src/services/pdf/fonts/`. Because Railpack's `bun install --frozen-lockfile` runs over the whole repo and the fonts are already committed source files, both are included automatically — we didn't find a gap here. If you add a *new* binary/wasm runtime asset later that isn't pulled in by `bun install` or isn't a committed repo file, Railpack has no step for "copy this extra file into the image" the way a Dockerfile's `COPY` does; you'd need a `steps.*.commands` entry in a `railpack.json`, or switch that service back to [Docker Compose](/docs/deployment/coolify-docker-compose).

## Verifying locally

Install the CLI and try a dry-run plan before trusting it to a platform:

```bash
curl -fsSL https://railpack.com/install.sh | sh
railpack info . --build-cmd "cd apps/server && bun run build" \
  --start-cmd "bun packages/db/src/migrate.ts && bun apps/server/dist/index.mjs"
```

Swap in the web app's commands to check that plan too. `railpack build` needs a local BuildKit daemon (`docker run --rm --privileged -d --name buildkit moby/buildkit` + `export BUILDKIT_HOST='docker-container://buildkit'`) if you want to produce a real image rather than just a plan.
